## 全局约束

- **一页一个问题**：页标题写成问题或结论句，比如“为什么压 32 倍还不够？”，不要只写“FastViT 结构”这种名词。
- **一页最多一张主图**：图用来帮大家看懂，不用来证明。实验表格、跑分不上页。
- **页面上只放关键词**：每页正文不超过 3 行，完整的话放在讲稿里。
- **数字只留能让人一下看懂的**：token 数、位置数、下采样倍数。
- **术语全程统一**：视觉编码器、stage、压缩（下采样）、token、卷积、自注意力。
- **颜色全程统一**，沿用论文原图：卷积 stage 用灰色，自注意力 stage 用米色，我们要指出的问题用红色标注。

## 第 1 部分：高分辨率下慢在哪？

### P1 · 分辨率越高，VLM 越慢

- **图**：自己画一个简单的对比：ViT 在 336² 下 576 个 token，在 1024² 下约 5300 个 token。用两个大数字或两根柱子就行。
- **页面上**：TTFT = 视觉编码时间 + prefill 时间；ViT 的 token 数随分辨率平方增长。
- **讲**：接前一位同学。ViT 从头到尾不降采样，图越大 token 越多，每层都要对所有 token 做自注意力。

### P2 · 光减少 token 还不够

- **图**：FastVLM Fig. 5（[ttft_breakdown.png](../paper/figures/ttft_breakdown.png)）。
- **页面上**：分辨率一高，视觉编码本身就是大头。
- **讲**：
  - 先说清楚这张图画的是**论文自己的模型**：token 已经压得很少了，可分辨率一高，编码时间还是占大头。
  - 所以剪枝这类“只减 token”的做法不够；切图更糟，编码次数更多。它们都是在 ViT 外面打补丁。
  - 抛出问题：能不能换一个天生适合高分辨率的编码器？

## 第 2 部分：前人的编码器长什么样？

### P3 · FastVLM 只换了流水线里的一个框

- **图**：自己画三框流水线：视觉编码器 → 投影层 → LLM。把视觉编码器框高亮，框里放 FastViT 的 stage 列（[放大 A 原图](figures/zoomA_fastvit_stage_column.png)）。
- **页面上**：只换视觉编码器，投影层和 LLM 沿用 LLaVA。
- **讲**：后面讲的 stage 全都是这个框里面的结构。

### P4 · 前作 FastViT：金字塔 + 混合

- **图**：[放大 A 原图](figures/zoomA_fastvit_stage_column.png)，单独放大。
- **页面上**：每过一个 stage 缩小一次；前 3 个 stage 用卷积，最后 1 个用自注意力；最后剩几个位置，就是几个 token。
- **讲**：
  - 和“切块”对比：ViT 一开始就切好、token 数不变；金字塔是一边算一边缩小。
  - FastVLM 的第一步就是直接拿 FastViT 来用，方向是对的。但推到更高分辨率、再把模型放大时，问题就出来了。
- **可选**：角落里放一个小的 RepMixer 图（[放大 C](figures/zoomC_fastvit_repmixer.png)），一句话说“卷积部分是好设计，后面原样保留”。也可以放到备用页。

## 第 3 部分：哪里不适合高分辨率？（重点）

### P5 · 压了 32 倍，为什么还不够？

- **图**：[放大 A 标注版](figures/zoomA_fastvit_stage_column_annotated.png)，在最后标红“1024² → 32×32 = 1024 个 token”。
- **页面上**：1024 个 token 交给 LLM，还是太多。
- **讲**：已经压了 32 倍，能不能再压？

### P6 · 自注意力放得太早

- **图**：[放大 B](figures/zoomB_fastvit_stage4_attention.png) 放在左边；右边放一张小表：

  | stage 3（压 16 倍） | 位置数 | 自注意力开销 |
  |---|---|---|
  | 224² 小图 | 14×14 = 196 | 便宜 |
  | 1024² 大图 | 64×64 = 4096 | 贵约 400 倍 |

- **页面上**：底部一句结论：**病根是压得不够**。
- **讲**：
  - 按四步讲：想把模型放大 → 习惯在 stage 3、4 多堆自注意力 → 这些设计原本面向小图 → 换成大图，开销爆炸。
  - 最后把 P5 和 P6 合起来说：做自注意力之前压得不够，计算爆炸；交给 LLM 之前压得不够，token 太多。

## 第 4 部分：怎么改？为什么这样改能行？（重点）

### P7 · 再压一层

- **图**：两张竖图并排，标注风格一致，自注意力 stage 都用红框标出：
  - 左：[FastViT 标注版（无插图，和右图等高）](figures/fastvit_stage_column_annotated_p7.png)，4 个 stage，压到 32 倍；
  - 右：[FastViTHD 标注版](figures/fastvithd_stage_column_annotated.png)，5 个 stage，压到 64 倍。
- **页面上**：1024² 下的 token 数：ViT 约 5300 → FastViT 1024 → FastViTHD 256。
- **讲**：一个改动同时治好 P5 和 P6。自注意力挪到已经压到 32 倍、64 倍的地方。

### P8 · 为什么别人没早这么做？

- **图**：自己画一个示意：一张有小字的图，上面叠一个网格；压得越狠，网格越粗，一格里塞进好几个字。
- **页面上**：压得越狠，细节越容易丢。
- **讲**：
  - 当时的主流看法甚至是往少里压：ViTamin 建议总共只压 16 倍。
  - 所以真正的问题是：怎么压，才能不丢东西？

### P9 · 怎么压到点上

- **图**：[FastViTHD 横版标注图](figures/fastvithd_stages_p9_annotated.png)，已经标好三处：
  - ① 前 3 个卷积 stage 上方的括号；
  - ② 每个 stage 上方的通道数，从 96 到 1536；
  - ③ 图下方的多尺度支路。
- **页面上**：三个短语，和图上序号一一对应：先看细节再压缩；空间换通道；多尺度特征。
- **讲**：
  - ① 图还大的时候，用便宜的卷积把细节处理掉；压小以后，才做自注意力。
  - ② 长宽减半、通道翻倍，信息尽量挪进通道里，而不是直接扔掉。
  - ③ 从前面几个 stage 把细节再拉回来。

### P10 · 压缩换来的是分辨率

- **图**：自己画两张图并排，都是 16×16 的网格，也就是 256 个 token：左边是 224² 的模糊小图（ViT），右边是 1024² 的清晰大图（FastViTHD）。
- **页面上**：同样 256 个 token，能看的分辨率差了约 4.6 倍（1024 / 224，按边长算）。
- **讲**：对 VLM 来说，分辨率才是关键。压缩不是牺牲。

## 第 5 部分：还要付出什么代价？

### P11 · 代价与收尾

- **图**：不放。
- **页面上**：两条代价，加一句收尾。
  1. 压得狠，对训练要求更高
  2. 分辨率要和 LLM 大小匹配
  - 收尾：从编码器内部重新设计，而不是在外面打补丁。
- **讲**：
  - 第 1 条：每个 token 要装更多信息，背后是一套很强的图文预训练（大数据，加大模型当老师）。
  - 第 2 条：给很小的 LLM 喂超高分辨率的图，它也用不上，整个系统要两头一起调。
